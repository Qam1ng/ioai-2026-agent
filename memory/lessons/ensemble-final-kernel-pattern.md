Final-submission ensemble pattern that works for code competitions (train-in-kernel): run the cheap/robust pipeline FIRST and write a provisional submission, then run the expensive pipeline inside try/except (skip on CPU) and blend probs with OOF-fitted hard-coded weights. Share expensive preprocessing (audio decode/resample) via one cached pass. Smoke-test BOTH the blend path and the forced-failure fallback path locally before pushing. Caveats observed: (1) an OOF-CV-winning blend (0.2*finetune + 0.8*frozen-features, +0.005 OOF) scored slightly BELOW the best single model on a small public split (0.80476 vs 0.80732) — with ~920 train rows and ~363 test rows, CV deltas <0.01 do not reliably transfer; blending is still the right expected-value pick but don't promise gains. (2) The kaggle MCP kernel_log tool can return a stale/wrong log; verify what actually ran by downloading output with `kaggle kernels output <ref>` and checking your own log line signatures. (3) Python 3.14 ProcessPoolExecutor uses forkserver: module-level code re-executes in workers, so keep heavy work behind `if __name__ == "__main__"` and make module level idempotent.
